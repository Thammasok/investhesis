# API (`apps/api`)

In `apps/api` (`@pacta/api`, Node 24 + Fastify 5, TS run natively by Node type stripping in dev): `pnpm dev` (`node --watch --env-file-if-exists=../../.env --env-file-if-exists=.env src/main.ts`; copy `apps/api/.env.example` to `apps/api/.env` first, it is git-ignored and wins over a root `.env`; needs `NODE_ENV`, `DATABASE_URL`, `PUBLIC_WEB_ORIGIN`; port 8080), `pnpm build` (`tsc` → `dist/`), `pnpm start`, `pnpm lint` (oxlint), `pnpm typecheck` (`tsc --noEmit`), `pnpm test` / `pnpm test:watch` (Vitest; `pnpm test` runs the main suite, then the wall-clock files `*.timing.test.ts` and `*.bench.test.ts` alone in `vitest.timing.config.ts`, because next to CPU-heavy files they fail on a busy machine; name any new timing or p95 test that way). Config is read only in `src/config/env.ts`. The Docker image builds from the repo root (the lockfile is needed): `pnpm docker:build:api` = `docker build -f apps/api/Dockerfile -t pacta-api .`. Auth primitives live in `apps/api/src/modules/auth/` (T-007; routes come in T-008): `passwords.service.ts` + `passwords.logic.ts` (argon2id through `node:crypto`, same PHC format and parameters as `scripts/hash-password.mjs`, so seeded hashes verify; `@node-rs/argon2` from ADR-009 is not used), `codes.*`, `reset-tokens.service.ts`, `tokens/` (jose EdDSA access token, opaque refresh token), `sessions.*`, `rate-limiter.*`, `revocation-cache.service.ts`, `mail-outbox.service.ts`, `emails/`, and `auth.repository.ts` (all Drizzle queries for the auth tables; see "API layers" below). Each is a `create*` factory taking `db`, a `Clock` (`lib/clock.ts`; tests use `test/fake-clock.ts`) and config values; `createAuthPrimitives()` in `modules/auth/index.ts` builds them all and `buildApp` exposes them as `app.auth` when it gets a `DbHandle` and a mailer (it registers `rateLimiter.pruneExpired` on the ticker, `revocationCache.start()` on `onReady`, `mailOutbox.drain()` on `preClose`, `revocationCache.stop()` on `onClose`). Verification methods that count attempts (`CodeService.verify`) and session rotation return or throw only after their writes commit, so a failure never rolls back an attempt count or a family revoke. Config now requires `JWT_PRIVATE_KEY` (Ed25519 PKCS#8 PEM) and `OTP_PEPPER` (base64, at least 32 bytes), both from `node scripts/gen-dev-keys.mjs`; optional: `JWT_PREVIOUS_PUBLIC_KEY`, `JWT_ISSUER`, `JWT_AUDIENCE`, `ACCESS_TOKEN_TTL_SECONDS`, `REFRESH_IDLE_TTL_SECONDS`, `REFRESH_ABSOLUTE_TTL_SECONDS`, `REFRESH_COOKIE_NAME`, `REFRESH_COOKIE_PATH` (`/api/auth`), `OTP_TTL_SECONDS`, `OTP_RESEND_SECONDS`, `REVOCATION_POLL_MS`; `test/env.ts` generates throwaway keys for tests. `pnpm --filter @pacta/api test:coverage` runs Vitest with v8 coverage over `src/modules/**` and fails below 85 % lines. Sessions and identity (T-009): `plugins/authenticate.ts` is an `onRequest` hook on every route except `PUBLIC_PATHS` (health, ready, openapi, the `/auth/*` routes), including unknown paths (401 `missing_token` before 404); it verifies the bearer token with `AccessTokenService` and checks `sid` against `RevocationCache` with no I/O, and sets `req.identity` (`verifyBearer` is exported; `src/plugins/authenticate.bench.test.ts` asserts p95 < 1 ms, measured about 0.06 ms). A new public route must be added to `PUBLIC_PATHS`. `modules/auth/session.routes.ts` has `POST /auth/refresh` and `/auth/sign-out` (cookie plus `x-pacta-csrf: 1`, checked first; refresh is rate limited per IP; `SessionService.onReuseDetected` logs `auth.refresh.reuse_detected`). `modules/users/` (`avatar-catalog.ts` holds the pinned lists: `PARTS` (9 notionists parts, variant names as in DiceBear 10.6.0), `AVATAR_BACKGROUNDS` (12 `#rrggbb`); the six seed styles are gone (T-010, ADR-019); `users.schemas.ts` holds `avatarSchema` (one strict object: `kind` `parts`, `style` `notionists`, nine parts of which six are required and `glasses`/`beard`/`gesture` nullable; optional `background` from the palette; a `kind: 'seed'` value is 400 `validation_failed`, so `/openapi.json` shows a single object with no `oneOf`), `meBody`, `patchMeBody` (a legacy `{style, seed}` or seed body answers 400 `validation_failed`); `displayNameSchema` is shared from `auth.schemas.ts` and rejects NUL) has `UsersService.loadCurrentUser` (user plus memberships in one query) and `GET /me` (includes `user.avatar`: a parts value or `null`, and `null` (also for a leftover seed value) plus one `users.avatar_invalid` warn log (no value) when the stored JSON no longer validates; the column is `app.users.avatar jsonb`, changesets 0009 and 0010, shape (`kind = 'parts'`) and size checked by the DB and values by the API; 0010 converted seed rows to deterministic parts avatars (md5 of the user id per part); its preHandler sets `req.currentUser`, and tenant scope always comes from those memberships), plus `PATCH /me` (`updateProfile`: strict body, at least one of `displayName` / `avatar`, `avatar: null` removes it; rate limit `profile:user:<id>` 30 per 600 s through `auth.rateLimiter`; 401 `invalid_token` when the row is gone; logs `users.profile_updated` with `changed` field names only, never the name or seed; `toProfilePatch` is the pure body-to-columns step). Test helpers: `test/session-helpers.ts` (`signedIn`, `addMembership`, `bearer`, `CSRF`). Sign-up, sign-in and recovery (T-008): `modules/auth/auth-flow.routes.ts` (Zod schemas in `auth.schemas.ts`, flows in `auth.service.ts`, queries in `auth.repository.ts`) serves `POST /auth/sign-up | verify-email | resend-code | sign-in | forgot-password | verify-recovery | reset-password | change-password`. Enumeration safety: sign-up, forgot and resend answer `202 { refCode, resendAvailableAt }` for every address (a random ref when nothing is sent), sign-up hashes the password and sign-in runs one argon2 verify (`dummyVerify` when unknown or over 128 chars) on every path. Send limits are keyed by the address hash, not the user row: `cooldown:<purpose>` (1 per `OTP_RESEND_SECONDS`, the only source of `Retry-After` for resend), `send:email`, `send:ip`; sign-in uses `signin:ip` and `signin:email`; verify-email and verify-recovery share `verify:email`; change-password uses `password_change:user` (5 per 15 min, keyed by the authenticated user). `POST /auth/change-password` (T-004, account settings) is the one auth route that needs a bearer token (`req.identity`, never in `PUBLIC_PATHS`): it checks the rate limit first, verifies the current password (`dummyVerify` when the user has none), judges the new one with `judgeNewPassword` (weak before same — ADR-002, so `changePasswordBody` only caps lengths), then stores the hash and revokes the other session families in one transaction, `notifyRevoked` feeds the revocation cache after the commit, and the bilingual `passwordChanged` notice mail is queued; failures answer `400 invalid_credentials | weak_password | same_password` and log `auth.password_change.fail` with the reason. A sign-in of an unverified user inside the cooldown is still 403 and mails nothing (Q-4); a repeat sign-up inside it is 429 (Q-3). `AppError` takes optional `headers` (the error handler sets them, used for `Retry-After`). Security events are logged as `{ event, userId? }` and never carry an email, code or token. Route tests use `test/auth-flow-helpers.ts` (`createHarness`: real per-file DB, FakeMailer, FakeClock, captured log stream, codes read from the mailer outbox; each request gets a fresh remote IP unless `ip` is passed); `test/auth-flow.timing.test.ts` is the NFR-002 p95 check (50 runs per case, under 50 ms).

## API layers and idempotency

API layers (T-018; `.claude/knowledges/microservice_testing_strategy.md` adapted to Fastify, Drizzle and Vitest). Each layer calls only the layers below it, and files are classified by suffix, in kebab-case, inside `modules/<module>/` (subfolders such as `emails/` and `tokens/` keep the same suffixes):
- Resource, `*.routes.ts` (and `*.schemas.ts`, `refresh-cookie.ts`): parse, validate, format the response, nothing else. Never imports a repository, `db/` or `drizzle-orm`; it takes a service (or primitives) through plugin options, which `app.ts` wires.
- Service, `*.service.ts`, `auth/index.ts` (composition): rules, orchestration, logging, no `req`/`reply`. Reaches data only through `*.repository.ts`; opens transactions with `inTransaction(db, fn)` and gets the `Db`/`Executor` types from the repository. Never imports `db/` or `drizzle-orm`. Primitives (sessions, rate limiter, mail outbox, ...) are services with `create*` factories.
- Domain, `*.logic.ts`: pure functions of their arguments (password policy, code hashing and verdicts, rotation verdicts, rate-limit verdicts, email templates, `toCurrentUser`). No `db`, repository, integration or service imports, and no clock or randomness: `now` and a `RandomInt` are passed in.
- Repository, one `*.repository.ts` per module (`auth/auth.repository.ts`, `users/users.repository.ts`): all Drizzle queries, taking a `Db` or `Executor`. Only repositories and `db/` import `drizzle-orm`.
- Gateway: `integrations/` (unchanged; vendor imports are guarded by `check:integrations`).
Pick the simplest call pattern that fits (Resource to Service to Repository, plus Domain when there is real logic); do not add a layer that adds nothing. `scripts/check-layers.mjs` enforces the import rules (fixtures in `scripts/__tests__/guards.test.mjs`). Tests sit next to their subject: `*.logic.test.ts` and `*.service.test.ts` are unit tests (services that need a database use `createTestDb()`), `*.repository.test.ts` are integration tests on the test DB, and routes are covered with `fastify.inject` in `apps/api/test/` (the `tc-*.test.ts` catalogue files stay there).

Idempotency (T-019): `Idempotency-Key` support is infrastructure only, and no route uses it yet. A route opts in with `config: { idempotency: { required: boolean } }` (`required: true` answers 400 without the header); `plugins/idempotency.ts` adds the hooks for that route and fails startup when a `/auth/*` or `PUBLIC_PATHS` route, a `GET`/`HEAD`/`OPTIONS` route, or a malformed config opts in. Spread `idempotencyDocs({ required })` from `modules/idempotency/idempotency.schemas.ts` into the route `schema` (and merge its `response`) so `/openapi.json` documents the header and the errors. Keys are per user, method and route; the fingerprint covers method, route pattern, params, query and body. Error codes: `idempotency_key_required` (400), `idempotency_key_invalid` (400), `idempotency_in_progress` (409, `Retry-After`), `idempotency_key_reused` (422). Only 2xx JSON or empty responses up to 64 KB are stored (allowlisted headers `content-type` and `location`, never `set-cookie`); everything else releases the key; a replay carries `Idempotent-Replayed: true`. Config: `IDEMPOTENCY_TTL_SECONDS` (86400) and `IDEMPOTENCY_LOCK_SECONDS` (30, stale-lock takeover); the `idempotency.prune` task runs on the `MaintenanceTicker`. Code is in `modules/idempotency/` (`*.logic.ts`, `*.service.ts`, `*.repository.ts`); tests use the test-only routes in `apps/api/test/idempotency-routes.ts`, never production wiring. See `design.md` §Idempotency and ADR-020.

## Jobs queue and worker (`modules/jobs/`, `lifecycle/job-worker.ts`)

`app.jobs` is the queue (ADR-012, ADR-013): `JobsService.enqueue(tx, { tenantId, type, payload, dedupeKey?, maxAttempts?, runAt? })` writes through the caller's transaction and returns `{ id, created }`; an open (queued or running) job holding the same `dedupeKey` is returned with `created: false`. `claim(types)` is one `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)` over due jobs of the given types, oldest first, and counts the attempt. `locked_at` is both the heartbeat and the ownership token: `heartbeat`, `complete`, `fail` and `release` only match the claim's own `locked_at`, so a worker whose lock was reclaimed writes nothing. `fail` classifies the thrown value with `classifyError` (`jobs.logic.ts`: only `kind`, `transient === false` / `permanent === true` and `retryAfterMs` are read, so an `OcrError` works unchanged) and either requeues at `nextRunAt` (30 s, 2 min, 8 min, ... capped at 1 h, plus jitter, a longer `retryAfterMs` wins) or marks the job `failed` (permanent error, or `attempts >= max_attempts`). `last_error` and the logs hold the error kind only, never a message; an unrecognised error is kind `internal` and retried. `reclaimStale()` (the `jobs.reclaim` task on the `MaintenanceTicker`) requeues running jobs not touched for `JOB_LOCK_TIMEOUT_MS` (`last_error = lock_expired`), or fails them when no attempt is left.

`createJobWorker` (`lifecycle/job-worker.ts`) takes handlers by job type (`buildApp({ jobHandlers })`, `(job, { signal, heartbeat }) => Promise<void>`) and claims only those types. It polls every `JOB_POLL_INTERVAL_MS` when idle and again at once after each job, runs at most `JOB_WORKER_CONCURRENCY` jobs, and heartbeats each running job every `JOB_LOCK_TIMEOUT_MS / 3`. `stop()` (an `onClose` hook registered after the db and storage hooks, because Fastify runs `onClose` last-registered-first) claims nothing more, aborts every running job's `signal`, returns it to `queued` with the attempt given back, and resolves without waiting for a handler that ignores the signal. `JOB_WORKER_ENABLED=false` leaves `app.jobWorker` undefined: the API starts and never claims. `pump()` and `idle()` let tests drive the worker with no timers. Config: `JOB_WORKER_ENABLED` (true), `JOB_WORKER_CONCURRENCY` (2, 1 to 16), `JOB_POLL_INTERVAL_MS` (1000), `JOB_LOCK_TIMEOUT_MS` (300000, at least 1000). Tests: `jobs.logic.test.ts` (TC-U-005..009), `jobs.service.test.ts`, `lifecycle/job-worker.test.ts`, `test/jobs-wiring.test.ts`.

## File storage (`integrations/storage/`)

`StorageProvider` (`storage.ts`: presigned PUT/GET, `head`, `readRange`, `put(key, bytes, contentType)` (server-side write that replaces an existing object and stores the type, for page images; the object is then served by `createDownloadUrl` with that type), `read(key)` (the whole object, `not_found` when missing; the API never sends these bytes to clients), `copy` onto an absent key only, idempotent `delete`, `StorageError` kinds `precondition | not_found | denied | unavailable`) has two implementations: `GcsStorage` (`gcs-storage.ts`, the only importer of `@google-cloud/storage` and `google-auth-library`, V4 signing; upload URLs sign `Content-Type` and `x-goog-content-length-range: N,N`; download URLs set response type and an RFC 6266 `filename*=UTF-8''` disposition; the signed query is never logged, see `redactSigned`) and `FakeStorage` (in-memory, opaque `fake://` URLs, helpers `put(signedRequest, body)` (an overload next to the port's `put(key, bytes, contentType)`), `get`, `seed`, `keys`; built only by tests). `createIntegrations(config)` returns `{ mailer, storage }`; it throws a `ConfigError` without `STORAGE_DRIVER=gcs` and `GCS_BUCKET`. Signing uses the local key when `GCS_CLIENT_EMAIL` and `GCS_PRIVATE_KEY` are both set (a `JWT` auth client, because GoogleAuth's `credentials` option is deprecated); with neither it signs keyless through IAM.

The shared contract suite `storage.contract.ts` runs in `pnpm test` against `FakeStorage` and against fake-gcs-server (bucket `pacta-test`, `GCS_API_ENDPOINT` or `http://127.0.0.1:${PACTA_GCS_PORT:-4443}`) in `gcs-storage.test.ts`, so `pnpm test:api` needs `pnpm stack:up` first. fake-gcs-server 1.56.1 enforces neither `x-goog-content-length-range` nor the `ifGenerationMatch: 0` copy precondition, so those two cases (TC-U-012, TC-U-015) run only where the harness sets `enforcesSignatures: true` (`FakeStorage`, and the real-bucket run in T-011).

Variables (all in `config/env.ts`; empty values count as unset): `STORAGE_DRIVER` (`gcs`), `GCS_BUCKET` (`pacta-dev` locally, `pacta-test` in tests), `GCS_PROJECT_ID` (required unless `GCS_API_ENDPOINT` is set), `GCS_API_ENDPOINT` and `GCS_PUBLIC_ENDPOINT` (emulator only, the public one defaults to the API one and is the origin written into signed URLs; both are rejected when `NODE_ENV=production`), `GCS_CLIENT_EMAIL` + `GCS_PRIVATE_KEY` (together or neither), `UPLOAD_URL_TTL_SECONDS` (900, max 900), `VIEW_URL_TTL_SECONDS` (300, max 300), `UPLOAD_MAX_BYTES` (20971520, must equal the web `MAX_UPLOAD_BYTES`), `UPLOAD_INTENT_RATE_PER_MINUTE` (60, per user). Local values are in `apps/api/.env.example`.

## Folders (`modules/files/`)

`GET /folders` (`parentId` omitted = root, `q`, `sort` of `name|-name|createdAt|-createdAt`, default `name`, Thai ICU collation `th-TH-x-icu`, ties on id), `GET /folders/:id` (ancestor `path`, root first, one recursive CTE), `POST /folders`, `PATCH /folders/:id` (`name` and/or `parentId`, null moves to the root), `DELETE /folders/:id` (empty only). Layers: `folders.routes.ts` / `folders.schemas.ts` -> `folders.service.ts` -> `files.repository.ts`, with `folders.logic.ts` (audit action and metadata) and `scope.service.ts` (`resolve(userId)` gives `{ tenantId, userId }` from the user's oldest membership, 403 `no_tenant` without one; later files services reuse it). A move takes `pg_advisory_xact_lock` per tenant (ADR-011) and then checks the target's ancestors for a cycle (400 `folder_cycle`); `23505` becomes 409 `folder_name_taken`, an FK violation on delete 409 `folder_not_empty` and on create or move 404 `folder_not_found`. Another tenant's id is a 404 like an unknown one. Audit: `folder.created | renamed | moved | deleted` in the same transaction, with `from` and `to` name and parent on a change. Tests: `modules/files/folders.service.test.ts` (TC-U-031..041, real DB) and `test/folders.routes.test.ts` (routes, OpenAPI, concurrent crossed moves, isolation rows 10 to 16).

## Uploads (`modules/files/`)

`POST /uploads` and `POST /documents {uploadId}` (T-007; `uploads.routes.ts` / `files.schemas.ts` -> `uploads.service.ts` -> `uploads.repository.ts`, with `uploads.logic.ts` for the keys and the `StoredDocument` mapping). `buildApp` takes `storage` in `AppDeps` (`main.ts` passes the one from `createIntegrations`; the app closes it on shutdown) and registers the routes only when it has a db, auth and storage, so tests that omit `storage` have no upload routes. Intent: per-user rate limit first (`upload_intent:user:<id>`, `UPLOAD_INTENT_RATE_PER_MINUTE` per 60 s through `auth.rateLimiter`, 429 `rate_limited` with `Retry-After`; invalid intents past Zod count too, G16), then 415 `unsupported_file_type` (extension and lower-cased MIME must both match the table; a MIME parameter is a 415), 413 `payload_too_large` over `UPLOAD_MAX_BYTES`, 404 `folder_not_found`; the signed PUT binds `Content-Type` and `x-goog-content-length-range: N,N`; the row gets `url_expires_at` = now + `UPLOAD_URL_TTL_SECONDS` and `finalize_deadline` = that + 1 h. Body validation (400 `validation_failed`): strict objects, file name trimmed and at most 200 characters without `/`, `\` or control characters, `sizeBytes` an integer of at least 1, ids GUIDs; `typeHint` (the six document types) and `ocrLanguage` (`th+en | th | en`) are stored on the document and decide the OCR read (see "Read flow"). Finalize runs in one transaction that holds `SELECT ... FOR UPDATE` on the intent (so concurrent finalizes serialize, and the storage calls happen under that lock): unknown or other-tenant intent (or one cascaded away with its folder) 404 `upload_not_found`; already finalized 200 with the same document (ADR-014; the first call is 201); `now > finalize_deadline` 410 `upload_expired` (inclusive at the deadline, the URL expiry is not the gate); `head` missing 422 `upload_incomplete` (nothing queued, a retry after the PUT works); size differs 422 `upload_incomplete`; first 4 KiB fail `sniff` 422 `file_content_mismatch` (so a 1-byte file always fails, G7); both 422s queue the staging key in `storage_deletions` (`finalize_failed`) and commit before answering; then `copy` to `tenants/<tenant>/documents/<docId>`, insert the document (MD5 and CRC32C from `head`), mark the intent, audit `document.uploaded`, queue the staging key (`staging_finalized`). A failure after the copy rolls back and queues the permanent key with one `INSERT ... WHERE NOT EXISTS (document with that key)`, so a document row never points at a missing object. `StorageError` `unavailable` answers 503 `storage_unavailable` and leaves the intent open. A folder deleted while a finalize into it runs is 404 `folder_not_found` for the finalize (foreign-key violation or deadlock victim, SQLSTATE 23503 or 40P01) and 409 `folder_not_empty` for the delete when it is the deadlock victim. The API never deletes objects inline; `storage_deletions` rows are drained by the cleanup task (T-008). Tests: `uploads.service.test.ts` (TC-U-042..054, real DB, FakeStorage), `uploads.logic.test.ts`, `test/uploads.routes.test.ts` (routes, OpenAPI, 61st-request 429, sequential and concurrent finalize, and one flow against fake-gcs-server with the real `GcsStorage`; that emulator enforces no length range and no copy precondition).

## Documents (`modules/files/`)

`GET /documents` and `GET /documents/:id/file` (T-008; `documents.routes.ts` / `files.schemas.ts` -> `documents.service.ts` -> `documents.repository.ts`, which `buildApp` registers whenever it has a db and storage; `uploads.service.ts` still owns `POST /documents`). Listing: `folderId` omitted = root, an unknown or foreign folder is 404 `folder_not_found` (G4), a malformed id 400; `q` is a case-insensitive contains search of at most 100 characters (`%`, `_` and `\` are escaped, so they match literally); `sort` is `-createdAt` (default), `createdAt`, `name`, `-name`, `-size`, `size`, always with `id` ascending as the tie-break (names use `COLLATE "th-TH-x-icu"`; CLDR's Thai tailoring ignores punctuation, so `ก1.pdf` sorts before `ก.pdf`, unlike what TC-A-1245 expects); `page` from 1 (0, negative or non-numeric is 400, a page past the end is `200` with `items: []`), `pageSize` 1..100 (default 24, the web default), `total` counts the folder after `q`. Only the folder's own documents are listed, not descendants'. The default sort reads `documents_folder_listing`. File URL: a fresh signed GET per call (`VIEW_URL_TTL_SECONDS`, `Cache-Control: no-store`) with the stored MIME type; `download=1` adds an attachment disposition under the current `original_filename` (`0` and an empty value are a plain view, anything else 400 `validation_failed`); audit `document.viewed` or `document.downloaded` (metadata: the page number when one was asked for, never the file name, which often carries a party name) is written after signing, so a failed signing leaves no row; `StorageError` `unavailable` is 503 `storage_unavailable`. Tests: `documents.service.test.ts` (TC-U-055..058), `test/documents.routes.test.ts` (imports the web's `documentPageSchema` from `apps/web/src/features/files/api/schemas.ts`, read-only, and parses real responses with it), `test/documents-listing.bench.test.ts` (TC-A-1252: 10,000 documents, p95 at most 200 ms for each sort, `EXPLAIN` uses `documents_folder_listing`; runs in the serial timing pass).

`PATCH /documents/:id { originalFilename?, folderId? }` (strict body, at least one field; extra keys such as `status` are 400, G12): the name goes through `checkFileRename` (trimmed, at most 200 characters, no separators or control characters, same extension compared case-insensitively so `a.PDF` is allowed, G9; duplicates in a folder are fine) and a failure is 400 `validation_failed` with `errors[0].path = originalFilename`; `folderId` null moves to the root, an unknown or foreign target is 404 `folder_not_found` (checked in the service, with an FK violation from a folder deleted mid-request mapped to the same 404); the storage key and object are never touched. The row is read `FOR UPDATE`, one audit row is written per fact that changed (`document.renamed` with `from`/`to` name, `document.moved` with `from`/`to` folder id) and a no-op writes nothing. `DELETE /documents/:id`: one transaction deletes the row, upserts `storage_deletions` (`document_deleted`) and audits `document.deleted`; after the commit the service deletes the object and the outbox row, and a store failure is only logged (warn), so the answer is 204 either way and the cleanup task finishes the job. Unknown or foreign ids are 404 `document_not_found` on both routes, a malformed id 400.

## Read flow (`modules/extraction/`)

Starting a read (ocr-extraction T-010). `read.service.ts` (`createReadService`; queries in `read.repository.ts`, pure rules in `read.logic.ts`) is built by `buildApp` whenever it has a db and registers `extraction.routes.ts` (`POST /documents/read`, `POST /documents/:id/reprocess`); `uploads.service.ts` gets it as `reads` and calls `enqueueAtFinalize(tx, ...)` inside the finalize transaction right after the document insert, so the document and its `app.jobs` row (`type ocr.read`, payload `{ documentId }`, `dedupe_key ocr.read:<id>`, tenant from the document) commit or roll back together. Only PDF, JPEG, PNG and WebP are readable; Word and Excel are stored and never queued. Over the daily cap (`OCR_DAILY_PAGE_CAP`) the document is stored `uploaded` with no job ("not read yet", FR-049). The cap rule is `used < cap` on `app.ocr_usage` for the current `Asia/Bangkok` day (`bangkokDay(now)`, UTC+7) checked when something is queued, never `used + pages <= cap`; pages are charged when a read succeeds, not at enqueue (G3), so the worker checks the same rule again when a read **starts** (`begin` in `read-job.service.ts`, first attempt only): if the tenant's day is already at the cap it does nothing and the job succeeds, leaving the document `uploaded` ("not read yet") or `needs_review` with its old extraction, with no provider call. A burst queued before the first success is charged therefore overshoots the cap by at most the reads already running (`JOB_WORKER_CONCURRENCY` per instance, up to `OCR_MAX_PAGES` pages each); a retry of a read already admitted is never turned away. The member asks again with Read (429 until the next Bangkok day). `typeHint` and `ocrLanguage` are stored on the document at finalize and replaced by the values of a later `POST /documents/read`.

`POST /documents/read { documentIds (1..50 GUIDs), typeHint?, ocrLanguage? }` (strict body) is always 200 for a valid body with one result per id, in request order: `queued`, `not_readable_type`, `already_processing`, `document_confirmed`, `document_not_found` (unknown or another tenant's id). One transaction locks the tenant's rows `FOR UPDATE` in id order (so overlapping requests serialize per document), decides with `readVerdict(doc, openJob)` (type first, then confirmed, then an open job or `processing`, else queue), and answers `429 ocr_quota_exceeded` with nothing queued only when the cap is reached AND at least one document would have been queued (G3). A repeated id is `queued` then `already_processing` (G4). A queued document keeps its status except `failed`, which goes back to `uploaded` with `failure_code`/`progress` cleared (a `needs_review` document keeps its extraction until the worker replaces it); one `document.read_requested` audit row per queued document (metadata: provider name). `POST /documents/:id/reprocess`: 404 `document_not_found`, `409 document_not_failed` for any other status (checked before the cap), `429 ocr_quota_exceeded`, else the same enqueue with `document.reprocessed`; it answers a `DocumentDetail` without extraction (`status uploaded`, `queued true`; the full detail is T-011). Deleting a document queues every `document_pages.storage_key` in `storage_deletions` (`document_deleted`) with the original, in the same transaction. Tests: `read.logic.test.ts` (TC-U-042, TC-U-044), `test/read-requests.routes.test.ts` (TC-A-1500..1535), `ops/finalize.ops.test.ts` (TC-A-1507, p95 of finalize with a read queued minus without, at most 50 ms).

Running a read. `buildApp` registers the `ocr.read` handler (`read-job.service.ts` `handle(job, ctx)`; rules in `read-job.logic.ts`, queries in `read-job.repository.ts`) when it has a db, storage and `ocr` (`AppDeps.pageImages` is the renderer, default `createPageImages()`, closed after the worker stops; tests pass `FakePages` from `test/ocr-doubles.ts`), merged under any `deps.jobHandlers`. One attempt: lock the document through the **job's** tenant (`jobs.tenant_id`, never the payload; a missing, deleted or foreign document, or a payload that is not `{ documentId: guid }`, throws the permanent `document_not_found` / `invalid_payload`, so the job fails with nothing written; a `confirmed` document is skipped and the job succeeds, so a re-read never overwrites a confirm) and set `processing` (progress 0, kept on a retry) -> `storage.read` the original -> `pageImages.render` (`OCR_MAX_PAGES`; a blank image is `unreadable`, G17) -> `storage.put` each stored page JPEG at `tenants/{t}/document-pages/{d}/{n}.jpg`, one progress step per page (`progressAt`: pages fill 0.1..0.4, classify 0.5, extract 0.9; `setProgress` only moves forward) -> one transaction replaces the `document_pages` rows and `page_count` and queues stale page keys -> `classifyDocument` when the document has no `type_hint` (then the type is the model's) -> `TemplatesService.forRead(tenant, type)` (the latest version when the job reaches this step; the run records `template_version` and the fields as `template_snapshot`) -> `extractDocument` with `OCR_PAGES_PER_CALL`, `OCR_TIMEOUT_MS` and the job's abort signal -> **one transaction**: lock the document, insert the `ocr_runs` row (`succeeded`, tokens summed over the calls, duration), delete the old header and lines and insert the new ones (typed columns plus `field_meta`/`custom_fields`; a value its column cannot hold, such as a date that does not exist or money past `numeric(18,2)`, is NULL with the text in `raw`, `toColumn`), set `needs_review`, `type`, `page_count`, `read_at` (first read only), `fields_found`/`fields_total`/`confidence` (`summarise`: 15 header fields plus 7 per line, custom fields not counted, G13), clear `progress` and `failure_code`, and add the pages to `ocr_usage` for the Bangkok day. `ctx.heartbeat()` runs after the read of the original, after storing pages, after classify and after extract, besides the worker's own timer. A failure is classified by `classifyFailure` (page problems keep their code and are permanent; every provider error is `ocr_failed`, permanent for `refused`/`rejected`/`misconfigured`; a missing original is `unreadable`; anything else is a transient `ocr_failed`): the attempt gets an `ocr_runs` row (outcome = the error kind, page problems `unreadable`, tokens 0; none for a store or database failure), and when the error is permanent or `attempts >= max_attempts` the document becomes `failed` with the code (`too_many_pages` also stores the real `page_count`) and `progress` cleared; between attempts it stays `processing` (G9). Old header and lines are never touched by a failure (G10), and `ReadFailure`/`ReadAbort` carry only the kind, so `jobs.last_error`, run rows and logs never hold document text. On shutdown or a lost lock the handler stops writing and the worker re-queues the job. A document deleted mid-read gets no rows; page images already stored are queued in `storage_deletions`. The `ocr.orphans` maintenance task (`sweepOrphans`) fails `processing` documents that have no open job (a crash that exhausted the job), so they can be reprocessed. Tests: `read-job.logic.test.ts` (TC-U-043, 045, 046), `test/read-job.test.ts` (TC-A-1540..1571 with `ScriptedOcr` and `FakePages`, plus one real-renderer test), `page-images.test.ts` (blank image, page count on `too_many_pages`). ## Save and confirm (`modules/extraction/`)

ocr-extraction T-012. `review.service.ts` (`createReviewService`; queries in `review.repository.ts`, rules in `review.logic.ts`) is built by `buildApp` beside the listing service and serves `PATCH /documents/:id/extraction` and `POST /documents/:id/confirm` from `extraction.routes.ts`. Both lock the document row `FOR UPDATE` (`lockDocuments`) inside one transaction, so two saves serialise and the second diffs against the first; 404 `document_not_found` (also for another tenant, before any validation of values) comes before 409. Body (`extractionUpdateBody`, strict): `type?`, `header?` (partial map of the 15 keys), `lineItems?` (`{ id | null, values }[]`, the whole table: a row left out is deleted, `id: null` adds a row, list order becomes `line_no`, a key a kept row leaves out is unchanged), `custom?` (by template field id) and `regionReads?` (field path to region read id, applied as described under "Region re-read"). A part left out is unchanged. The service builds the stored extraction (`buildExtraction`), diffs it (`diffHeader`, `diffCustom`, `diffLines`: values are compared after cleaning, so `9,523` equals `9523.00` and a trailing space is nothing, and a value the body repeats is never re-validated), validates only the changed values (`validateChange`: money 16.2, quantity 14.4, rate 0 to 100 with two places, ISO date that exists, branch 5 digits, currency three capitals, tax id digits and length only because a bad check digit is saved and flagged (G15), list value among the template options), and answers `400 validation_failed` with every bad path and writes nothing (paths: `header.<key>`, `line.<lineId>.<key>`, `lineItems.<index>.<key>` for an added row, `custom.<fieldId>`; messages such as `invalid_money`, `taxIdLength`, `unknown_line`, `duplicate_line`, `unknown_field`, `field_removed`, `not_in_options`). A changed value is stored in canonical form (money with two places) with `{ confidence: null, source: 'user', box: null, low: false, raw: null }`; every change adds a `field_corrections` row (`scope` `type | header | custom | line | line_added | line_removed`, old and new value, old source and confidence, the header's `run_id`, actor, time). Removed rows are deleted, added rows are stored with every cell `user`. After the writes `documents.fields_found/fields_total/confidence` are recomputed from the stored cells (`summaryOf`: every cell counts in the total, a typed value is found, the mean is over found cells that have a confidence, so a reviewer's value is left out) and `updated_at` set. A save that changes nothing (a pure reorder still renumbers lines, with no correction) writes nothing, not even `updated_at` or an audit row. Audit `document.edited` with `fieldsChanged` (a count, no values). Status other than `needs_review` is `409 document_not_editable`, so a confirmed extraction is read-only on every route. `confirm`: `needs_review` becomes `confirmed` with `confirmed_at`, `confirmed_by`, `updated_at`; `region_reads.text` of the document is cleared; audit `document.confirmed`; any other status is `409 document_not_reviewable`; low-confidence fields do not block it. Both answer the `DocumentDetail` (`buildDetail`, shared with `GET /documents/:id` but with no `document.viewed` row). Tests: `review.logic.test.ts` (TC-U-051..055, TC-U-1557..1560), `test/review.routes.test.ts` (TC-A-1600..1612, 1690, 1707, 1709).

## Region re-read (`modules/extraction/`)

ocr-extraction T-013. `region.service.ts` (`createRegionService`; queries in `region.repository.ts`, rules in `region.logic.ts`) serves `POST /documents/:id/region-reads { page, x, y, width, height, target }` from `extraction.routes.ts`; `buildApp` registers it when it has a db, storage, `ocr` and auth (the renderer is the same `pageImages` as the read job). `target` is `{ scope: 'header', key }` (one of the 15 keys), `{ scope: 'custom', key: <template field id> }` or `{ scope: 'line', lineItemId, key }`; the body is strict and a box outside 0..1 per value is 400 at the schema. Order: 404 `document_not_found` (also another tenant's), 409 `document_not_editable` unless `needs_review`, `checkRegion` (a box that leaves the page is 400 `validation_failed`, one under 1 % on a side 400 `region_too_small`), the page must exist (400, path `page`), the target must exist on this document (a line id of another document, a custom field the template no longer has or an unknown field is 400), then the per-user rate limit `region_read:user:<id>` (`OCR_REGION_RATE_PER_MIN` per 60 s through `auth.rateLimiter`, 429 `rate_limited` with `Retry-After`), so a request that fails validation costs no budget. The stored page JPEG is read from storage and cropped with `REGION_PADDING` (2 % of the page) and `REGION_MIN_SIDE` (short side lifted to 320 px, never past 1568), and one `region` call goes to the provider with `OCR_REGION_TIMEOUT_MS` as the timeout and as an `AbortSignal.timeout`; the prompt names the target's type (`kindWords`). The answer is validated (`regionValidator`), the value normalised as the target's type (`targetType`: the header or line key's type, a custom field's type through `customKind`) and the confidence fixed by `regionConfidence`: `0.90` when it normalises and passes its own check (a tax id needs its checksum), `0.50` otherwise (the unnormalised text is still returned as `value`); nothing read answers `value: null`, `text: null`, `confidence: null`. Any provider error or an invalid answer is `502 ocr_unavailable` with no retry, one `ocr_runs` row (`kind region`, outcome = the error kind, `created_by`) and no `region_reads` row. On success one transaction (it re-locks the document and answers 409 if a confirm won the race) writes the `ocr_runs` row, the `region_reads` row (box, target, `text`, `value`, `confidence`, `created_by`) and audit `document.region_read` (page, scope and key only, never the text). Reading changes nothing in the extraction. `PATCH /documents/:id/extraction` with `regionReads` (path to read id: `header.<key>`, `custom.<fieldId>`, `line.<lineId>.<key>`): a changed value whose path names a read of this document for that same target and whose cleaned value equals the read's value (`withRegionSources`, `sourceFor`) is stored with `source: "region"`, the read's box (`{ page, x, y, width, height }`) and confidence, its `field_corrections` row gets `new_source = 'region'` and `region_read_id`, and the read's `applied_at` is set; any other change (a value edited after the read, a read of another document or tenant, a read for another field, an added row's cell) is stored as `user`. Confirm clears `region_reads.text` (T-012). Tests: `region.logic.test.ts` (TC-U-056..059) and `test/region.routes.test.ts` (TC-A-1620..1636, 1707).

## Storage cleanup (`modules/files/`)

`StorageCleanupService.tick()` (`storage-cleanup.service.ts`, queries in `storage-cleanup.repository.ts`, pure rules in `storage-cleanup.logic.ts`) is registered by `buildApp` as the `storage.cleanup` task on the `MaintenanceTicker` (every `MAINTENANCE_INTERVAL_MS`, 5 min by default) whenever the app has a db and storage. One pass: (1) queue the staging key of every unfinalized intent past `finalize_deadline` as `intent_expired`, once (one statement sets `upload_intents.cleanup_queued_at`, changeset 0015, and inserts with `ON CONFLICT DO NOTHING`; without the marker the intent row, kept 7 days so a late finalize answers 410, would queue its key every tick); (2) delete every due `storage_deletions` object in batches of 100 (a missing object is not an error), removing the outbox row on success; a failure sets `attempts + 1`, `last_error` and `next_attempt_at = now + 1 min, doubling, capped at 1 h`, logs a warn and, from the 10th attempt on, an error (`storage deletion failed`, with key, attempts and reason, no URL); (3) delete `upload_intents` rows created more than 7 days ago (finalized or not, after step 1, so no staging key is lost). The other queue reasons are due at once. Tests: `storage-cleanup.service.test.ts` (TC-U-064, TC-U-065, TC-A-1457..1459, the failing-then-succeeding store, the grace) and `test/storage-cleanup.wiring.test.ts` (TC-A-1266: delete with the store down, then the real ticker finishes it).

## Extraction pipeline (`modules/extraction/pipeline/`)

`extractDocument(pages, template, hints, provider, opts?)` (`extract-document.ts`, ocr-extraction T-008) is the whole read as one pure function: classify page 1 (skipped with `hints.typeHint`), extract in chunks of `opts.pagesPerCall` (default 8, ADR-004), validate, normalise, ground boxes, merge, check, score, flag. Its only effect is the `OcrProvider` calls; it imports no database, repository, service or route code (`pipeline.static.test.ts`, plus `check:layers` for the `*.logic.ts` files), and the read job, the eval runner and any page crop all call it. `pages` are `{ pageNo, model: { jpeg }, small?: { jpeg }, text: TextItem[] }` (a subset of `RenderedPage`; `small` is the optional <= 1024 px classify image), the template is the `PipelineTemplate` structural subset of the templates contract (`locked` standard fields are matched to header columns by `STANDARD_OUTPUT_KEYS`; every unlocked non-table field is custom). The result has `header` (the 15 keys), `lineItems`, `custom` (template order, with the template's `fieldId`/`key`), `checks`, token `usage` and `promptVersion`; every value is `{ value, confidence, source: 'ocr', box, low }`. A validation failure throws `OcrError('invalid_output')` (all or nothing, FR-015); provider errors pass through.
- **Schema** (`schema.logic.ts`): one walk builds the JSON Schema and the strict Zod validator. Flat answer: the 15 header keys, `c_1..c_n` for custom fields (the tenant's key is never a property name; `customKeys` maps back to field ids) and `lineItems` of `{ cells, confidence, box }` per row. Only the strict subset (all properties required, nullable, `additionalProperties: false`, no numeric or length keywords); ranges (confidence 0..1, box `[page, x0, y0, x1, y1]` integers 0..1000) are Zod's. Unknown keys, including an own `__proto__`, fail.
- **Prompt** (`prompts/extract.v1.ts`, `PROMPT_VERSION = 'extract.v1'`): the system text is constant. The user turn holds server facts, then tenant labels, hints, rules and options only between `<<<TENANT_CONFIGURATION` and `END_TENANT_CONFIGURATION>>>`, then the PDF text layer only between `<<<UNTRUSTED_DOCUMENT_TEXT` and `END_UNTRUSTED_DOCUMENT_TEXT>>>`; `<` and `>` in inserted text become full-width, so nothing can close a block. A test asserts this on the built request. Add every new tenant- or document-derived string to a block, never outside.
- **Normalise** (`normalise.logic.ts`, FR-021): `normalise(kind, value, { stripSpaces, fixLookAlikes, options })` returns `{ value, raw }`; no typed value keeps the text as read (the pipeline stores it and caps its confidence below `reviewBelow`; unparseable values are skipped by the checks). Thai digits, Buddhist years (2400..2700 minus 543), Thai and English month names; money more than two places is refused unless the extras are zeros. Thai text is folded with `foldThai` (`text.logic.ts`): U+0E4D U+0E32 and U+0E33 U+0E32 both become U+0E33, on both sides of every comparison.
- **Checks** (`checks.logic.ts`, FR-022): a duplicate of the web's `runChecks` on BigInt units (`decimal.logic.ts`), plus `involved` field refs; `applyChecks` caps those fields below their own `reviewBelow`. The shared case table is `apps/web/src/features/documents/cases/checks.cases.json`; the API reads that file directly in `checks.cases.test.ts`, the web in `checks.cases.test.ts` beside `checks.ts`. Adding a rule means a case there, and `count` in the file must match: both runners have a meta-test that fails when a case is dropped from the table or filtered out of a runner.
- **Grounding and confidence** (`grounding.logic.ts`, `confidence.logic.ts`, ADR-005 and ADR-007): text-layer runs on one baseline band are joined before matching (value and raw text, spaces, commas and, for tax IDs, dashes ignored); a unique match gives the exact box (no padding), the model box is kept only when inside the page and non-degenerate; a text-layer match floors confidence at 0.95, no match on a page that has a text layer caps it at 0.70, a failed check or unnormalisable value caps at `reviewBelow - 1`. A missing value is `low` only when the template field is `required`. A line cell takes its row's confidence and box.
- Tests: `*.logic.test.ts` (TC-U-025..037), `extract-document.test.ts` (six types with `MockOcr`, injection, prompt boundaries, chunking), `pipeline.static.test.ts`.
